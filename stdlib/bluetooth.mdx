title: bluetooth
description: "Bluetooth Low Energy in both roles, through one set of objects:"
---

```gust
use bluetooth
```

Bluetooth Low Energy in both roles, through one set of objects:

- Central: `scan` for peripherals, `connect` to one, and drive its
  characteristics.
- Peripheral: `advertise` a GATT server other devices connect to.

A connected peripheral is a `Device`; a served database belongs to a
`Peripheral`. Both hand out the same `Service` and `Characteristic` types,
because GATT is symmetric about the attribute — only which side initiates
differs. A `Characteristic` is read with `read`, given a new value with `write`,
and asked what the other end pushed with `received`, whichever role it came
from.

Both roles work on the Raspberry Pi Pico 2 W (CYW43 + BTstack), on the ESP32
(NimBLE), and on the Linux host: there the central role uses BlueZ kernel
sockets (HCI scan + L2CAP ATT), and the peripheral role registers a GATT server
+ LE advertisement with BlueZ over D-Bus. Targets with no backend — macOS,
Windows, the browser — have no `bluetooth` package, so an import there is a
compile error rather than a misleading no-op. An ESP32 image needs a chip with
a Bluetooth radio, which the S2 has not. On Linux, both roles need privileges
(HCI scanning needs CAP_NET_RAW + CAP_NET_ADMIN; registering a GATT app and
advertisement with BlueZ is privileged too) — run as root.

Serial connections over the classic radio are a surface of their own, since a
device reached that way has no attributes to drive: `rfcomm_channel` asks a
device which channel it serves a profile on, `rfcomm_connect` opens that
channel, and `rfcomm_listen` serves one. Those exist on Linux only — the board
backends serve the low-energy roles alone.

UUIDs use the `UUID` type: `UUID(value: 0x181A)` (16-bit) or
`UUID(value: "0000180d-0000-1000-8000-00805f9b34fb")` (128-bit). Payloads are
`bytes`.

Example — scan, connect to the first result, and read a characteristic:
```gust
use bluetooth

def main() -> none
    HEART_RATE := bluetooth.UUID(value: 0x2A37)
    for info in bluetooth.scan(2000)
        with bluetooth.connect(info) as device
            print(device.characteristic(HEART_RATE).read())
        end
        return
    end
end
```

<Note>
Only available where `os == "linux" or has("ble")`.
</Note>

## `AdvertisingType`

<a id="AdvertisingType" />
```gust
enum AdvertisingType: integer
```

What one element of an advertising payload carries. Many more types are
defined than a peripheral has room to broadcast, so an element's type code
stays an `integer` and is compared against these.

**Variants**

- `flags = 1` — Discoverability and capability bits, which every connectable peripheral leads with.
- `services_16_incomplete = 2` — Some of the 16-bit service UUIDs published.
- `services_16_complete = 3` — All of them.
- `services_32_incomplete = 4` — Some of the 32-bit service UUIDs published.
- `services_32_complete = 5` — All of them.
- `services_128_incomplete = 6` — Some of the 128-bit service UUIDs published.
- `services_128_complete = 7` — All of them.
- `name_shortened = 8` — As much of the device name as there was room for.
- `name_complete = 9` — The whole device name.
- `tx_power = 10` — The power the packet was transmitted at, in dBm, which with `rssi` estimates distance.
- `services_16_solicited = 20` — 16-bit service UUIDs the device is looking for in a central rather than publishing itself.
- `services_128_solicited = 21` — The same, as 128-bit UUIDs.
- `service_data_16 = 22` — Data published under a 16-bit service UUID.
- `appearance = 25` — What the device looks like, as an assigned category code.
- `service_data_32 = 32` — Data published under a 32-bit service UUID.
- `service_data_128 = 33` — Data published under a 128-bit service UUID.
- `uri = 36` — A URI the device publishes, in the encoded form the specification defines.
- `manufacturer_data = 255` — Vendor-defined bytes, opening with the company identifier the vendor is registered under.

## `AttributeOpcode`

<a id="AttributeOpcode" />
```gust

```

something; a response answers exactly one request; a notification or

**Variants**

- `find_information_request = 4`
- `find_information_response = 5`

- `read_by_type_response = 9` — The attributes that request found.
- `read_request = 10` — Ask for one attribute's value.
- `read_response = 11` — That value.
- `read_by_group_type_request = 16` — Ask for every grouping attribute of one type in a range.
- `read_by_group_type_response = 17` — The groups that request found.
- `write_request = 18` — Set one attribute's value.
- `write_response = 19` — Acknowledgement that the write was applied.
- `handle_value_notification = 27` — A pushed value needing no acknowledgement.
- `handle_value_indication = 29` — A pushed value awaiting confirmation.
- `handle_value_confirmation = 30` — That confirmation.

## `AdvertisingKind`

<a id="AdvertisingKind" />
```gust
enum AdvertisingKind: integer
```

Which kind of advertising packet a report carries, which decides what
can be done with the advertiser. The values are the event types used on the
HCI wire.

A device is worth passing to `connect` only when it sent a `connectable`
or `directed` packet; the other kinds are broadcast-only, and a connection
attempt against one times out rather than failing quickly.

**Variants**

- `connectable = 0` — Open to a connection from any central, and answers a scan request. The common case.
- `directed = 1` — Open to a connection from one specific central, named in the packet, and carries no payload.
- `scannable = 2` — Answers a scan request but accepts no connection.
- `broadcast = 3` — Neither connectable nor scannable — a beacon.
- `scan_response = 4` — The answer to a scan request, carrying whatever did not fit in the advertisement itself.
- `unknown = 255` — An event type this package does not recognise.

## `DeviceInfo`

<a id="DeviceInfo" />
One advertising peripheral, as `scan` observed it. Pass it to `connect`
to start talking to the device.

A device broadcasts across several packets — an advertisement, and a scan
response when asked — and `scan` folds all of them into one `DeviceInfo`.
The parsed fields are the union of what those packets carried; `kind` and
`rssi` describe the packets themselves, and `advertisement` and
`scan_response` keep each payload as it arrived for anything this package
does not parse.

A field the device did not advertise is empty rather than absent, except
where a legal value would be indistinguishable from absence: `flags`,
`tx_power`, and `appearance` are `none` when unadvertised, since 0 means
something in all three.

```gust
def DeviceInfo

    address: string
    address_kind: AddressKind
    kind: AdvertisingKind
    name: string
    rssi: integer
    tx_power: integer | none
    services: list[UUID]
    solicited_services: list[UUID]
    service_data: list[ServiceData]
    manufacturer_data: bytes
    flags: integer | none
    appearance: integer | none
    uri: bytes
    advertisement: bytes
    scan_response: bytes

end
```

**Fields**

- `address: string` — The device's address, as "AA:BB:CC:DD:EE:FF". A device using a random address rotates it, so it is not a durable identity.
- `address_kind: AddressKind` — How that address was assigned.
- `kind: AdvertisingKind` — Which kind of advertising packet the device sent, which says whether `connect` can reach it at all. Never `scan_response`: a scan response is folded into the advertisement it answers.
- `name: string` — The advertised name, or "" when the device advertises none. A complete name is preferred over a shortened one.
- `rssi: integer` — Signal strength in dBm of the most recent packet, negative and closer to zero when nearer.
- `tx_power: integer | none` — The power in dBm the device transmits at, or `none` when it does not say. `tx_power - rssi` is the path loss, which is what a distance estimate is built on.
- `services: list[UUID]` — The service UUIDs the device advertises, which is often empty even on a device that publishes services once connected.
- `solicited_services: list[UUID]` — Service UUIDs the device is looking for in a central, rather than ones it publishes.
- `service_data: list[ServiceData]` — Data published under a service UUID, which is where a beacon protocol built on an assigned service carries its contents.
- `manufacturer_data: bytes` — The raw manufacturer-specific advertising payload, which opens with the assigned company identifier.
- `flags: integer | none` — The discoverability and capability bits, or `none` when the device advertises no flags element.
- `appearance: integer | none` — The assigned appearance code, or `none` when unadvertised.
- `uri: bytes` — The URI the device publishes, still encoded, or empty `bytes`.
- `advertisement: bytes` — The advertising payload exactly as it arrived.
- `scan_response: bytes` — The scan-response payload exactly as it arrived, or empty `bytes` when the device sent none.

## `Central`

<a id="Central" />
The central connected to a served `Peripheral`, as the link reports it.
`Peripheral.central` returns one for as long as that central stays
connected.

A peripheral learns far less about its peer than a central learns from
scanning: it is told the address it was reached at, not the advertising
payload behind it. A field the link does not carry is empty rather than
absent, matching `DeviceInfo`.

```gust
def Central

    address: string
    address_kind: AddressKind
    name: string
    mtu: integer

end
```

**Fields**

- `address: string` — The central's address, as "AA:BB:CC:DD:EE:FF".
- `address_kind: AddressKind` — How that address was assigned. A privacy-conscious central rotates a random address, so it is not a durable identity.
- `name: string` — The central's name, or "" when the link does not name it. Only a backend whose Bluetooth daemon already knows the peer fills this; on a board the peripheral would have to turn around and read the central's own name characteristic to learn it.
- `mtu: integer` — The negotiated attribute packet size in bytes, or 0 when the backend does not report one. A value longer than `mtu - 3` does not fit one packet and reaches the central truncated.

## `Characteristic`

<a id="Characteristic" />
One GATT characteristic, on either side of a connection.

Obtain one from `Device.characteristic`, `Service.characteristic`, or
`ServiceBuilder.add_characteristic`. The three operations mean the same
thing in both roles — read the current value, push a new one to the other
end, take what the other end pushed at us — so code driving a
characteristic does not care which side of the link it runs on.

```gust
def Characteristic

    uuid: UUID
    properties: list[Property]
    _peer: GattPeer
    _handle: integer

end
```

**Fields**

- `uuid: UUID` — The characteristic's UUID.
- `properties: list[Property]` — What the characteristic permits.
- `_peer: GattPeer` — The connection the attribute is reached through.
- `_handle: integer` — The attribute's value handle in the peer's database.

**Methods**

<a id="Characteristic.read" />
```gust
def Characteristic.read() -> bytes
```

The characteristic's current value.

On a remote characteristic this issues an attribute read and waits for the
response, bounded by the owning `Device`'s timeout. On a local one it
returns the stored value and cannot fail.

**Raises**

- `IOError` — If the peer is disconnected, or the read is refused or times out.

---

<a id="Characteristic.write" />
```gust
def Characteristic.write(data: bytes) -> none
```

Push `data` to the other end.

On a remote characteristic this issues an attribute write and waits for the
acknowledgement. On a local one `data` becomes the value a central reads,
and is sent to any central subscribed to notifications — which is why a
served characteristic needs no separate notify call.

**Parameters**

- `data` — The payload to write.

**Raises**

- `IOError` — If the peer is disconnected, or the write is refused or times out.

---

<a id="Characteristic.received" />
```gust
def Characteristic.received() -> bytes
```

Take what the other end last pushed to this characteristic, or empty
`bytes` when nothing has arrived since the previous call.

On a remote characteristic that is a notification from the peripheral,
which `Device.subscribe` has to ask for first. On a local one it is a write
from a connected central. Consuming, so each value is reported once.

---

<a id="Characteristic.permits" />
```gust
def Characteristic.permits(property: Property) -> bool
```

Whether the characteristic declares `property`.

**Parameters**

- `property` — The property to test for.

---

<a id="Characteristic.handle" />
```gust
def Characteristic.handle() -> integer
```

The attribute's value handle, for callers that speak the attribute
protocol directly.

## `Device`

<a id="Device" />
<Note>
Only available on Linux.
</Note>

An open connection to a peripheral. `connect` returns one; `close`, or
leaving the `with` block holding it, ends the connection.

**Implements:** [`GattPeer`](#GattPeer)

```gust
def Device implements GattPeer

    _fd: integer
    _open: ref[bool]
```

**Fields**

<a id="bluetooth.advertising_uri" />

The URI an advertising payload publishes, or empty `bytes` when it

<a id="bluetooth.build_advertising_payload" />
```gust
def build_advertising_payload(name: string, services: list[UUID]) -> bytes
```

The advertising payload a connectable peripheral broadcasts: the
discoverable flags, the device name, and as many of the 16-bit service
UUIDs as fit beside it.

Everything is fitted into the 31 octets one packet holds. A name too long
for what remains is carried shortened rather than dropped, and the service
list is marked incomplete when it did not all fit. A 128-bit service UUID is
left out: at 16 octets each they leave no room for a name, and a central
finds those services once connected.

**Parameters**

- `name: string` — The device name to advertise.
- `services: list[UUID]` — The service UUIDs the peripheral publishes.

---

<a id="bluetooth.uuid_from_wire" />
```gust
def uuid_from_wire(raw: bytes) -> UUID
```

The `UUID` a big-endian wire form denotes: a two-byte form becomes a
16-bit code, a sixteen-byte form the dashed 128-bit text.

A four-byte form is the 32-bit shorthand, which denotes the 128-bit UUID
that places those four bytes ahead of the Bluetooth base UUID. One whose
top two bytes are zero denotes the same UUID as the 16-bit code in its low
two bytes, and is returned in that shorter form so it compares equal to the
same service advertised either way.

**Parameters**

- `raw: bytes` — Two, four, or sixteen big-endian UUID bytes.

**Raises**

- `ValueError` — If `raw` is none of those three widths.

<a id="bluetooth.find" />
```gust
def find(name: string, service: UUID, timeout_ms: integer) -> list[DeviceInfo]
```

Scan for advertising peripherals and keep those matching every filter
given. An omitted filter matches anything, so `find()` is `scan`.

A peripheral that advertises no name, or none of its service UUIDs, cannot
match a filter on what it does not advertise — filter on `name` only for
devices known to publish one.

**Parameters**

- `name: string` — Advertised name to match exactly, or "" for any.
- `service: UUID` — Advertised service UUID to match, or the reserved 16-bit code 0 for any.
- `timeout_ms: integer` — Milliseconds to scan for.

---

<a id="bluetooth.scan" />
```gust
def scan(timeout_ms: integer) -> list[DeviceInfo]
```

<Note>
Only available on Linux.
</Note>

Listen for advertising peripherals for `timeout_ms` and return each one
seen, most recently reported first seen once.

A device that advertises repeatedly appears once, with the strongest
information gathered across its packets: many advertising packets carry no
name, so a name seen in any of them is kept.

Scanning takes the adapter away from the system's Bluetooth daemon for the
duration and hands it back before returning.

**Parameters**

- `timeout_ms: integer` — Milliseconds to listen for.

**Raises**

- `IOError` — If the adapter cannot be claimed, which usually means the process lacks CAP_NET_RAW and CAP_NET_ADMIN — run as root.

title: lvgl
description: "A widget UI toolkit, wrapping the LVGL rendering engine"
---

```gust
use lvgl
```

A widget UI toolkit, wrapping the LVGL rendering engine. Where the `drm` and
`framebuffer` packages hand back a raw pixel buffer, this draws laid-out, styled
widgets — labels, buttons, sliders, lists, charts, and more — with anti-aliased
text and pointer events.

Two displays are supported, one per platform. A Linux program presents straight
to `/dev/dri/card<index>` through LVGL's DRM backend (no window system
required), acquired with `start`. An ESP32 program drives an ST7789 panel over
SPI, brought up with `start_st7789` (see st7789.g). Everything above the
display — widgets, layout, styling, events, the render loop — is the same on
both.

Widgets are objects: a widget is created against a parent (the active `screen`,
or another widget) and configured through its methods — sizing, positioning,
styling, layout, and per-widget behavior. `on_click` and `on_event` route
interactions back into Gust functions. `run` enters the event loop and renders
until the process exits.

Nothing on screen has to hold still: `animate` moves a widget's property from
one value to another over time, and `timer` calls a function of yours on a
period. Both are driven by the same loop that draws, so a handler they run may
touch the interface directly.

Colors are 24-bit `0xRRGGBB` integers. Sizes and positions are in pixels. Style
methods take an optional `Part` and `State` to target a sub-component or an
interaction state (default: the widget's main part in its default state).

Presenting to a card is Linux-only, and requires DRM master (no compositor
owning the card).

The notes below are about the LVGL a native build links against; an ESP32 build
compiles LVGL into the firmware itself and configures it as described here
already.

The linked LVGL must be built with `LV_USE_STDLIB_MALLOC` set to
`LV_STDLIB_CLIB`. Its built-in allocator defaults to a 64 KB pool, and one
refresh that draws several dozen widgets can exceed it, because that frame's
draw tasks and any off-screen layers are all live at once. The default
`LV_ASSERT_HANDLER` halts in `while(1)`, so exhausting the pool shows up as a
process spinning at full CPU on a frame that never reaches the display, silent
because `LV_USE_LOG` defaults to 0. Building the same interface up across
several refreshes can stay under the ceiling, which makes the limit look
intermittent. Enabling `LV_USE_LOG` is worthwhile for the same reason, since
every failure path in the DRM backend reports only through it.

**Examples**

```gust
use lvgl

def main() -> none
    if not lvgl.start(0)
        return
    end
    screen := lvgl.screen()
    screen.set_bg_color(0x101828)

    panel := lvgl.container(screen)
    panel.set_size(300, 200)
    panel.center()
    panel.set_flex_flow(lvgl.FlexFlow.column)
    panel.set_flex_align(lvgl.FlexAlign.center, lvgl.FlexAlign.center,
        lvgl.FlexAlign.center)

    title := lvgl.label(panel)
    title.set_text("Hello, Gust")
    title.set_text_color(0x38BDF8)

    ok := lvgl.button(panel)
    ok.set_label("OK")
    ok.on_click(def () -> none
        title.set_text("Clicked")
    end)

    lvgl.run()
end
```

Only available on native builds and the ESP32.

## `Align`

<a id="Align" />
```gust
enum Align: integer
```

Anchor point used by `align` and `align_to` to position a widget
relative to its parent (or a reference widget). `out_*` variants place the
widget just outside the reference edge.

**Variants**

- `default = 0` — No alignment (keep the current position).
- `top_left = 1` — Parent's top-left corner.
- `top_mid = 2` — Centered along the parent's top edge.
- `top_right = 3` — Parent's top-right corner.
- `bottom_left = 4` — Parent's bottom-left corner.
- `bottom_mid = 5` — Centered along the parent's bottom edge.
- `bottom_right = 6` — Parent's bottom-right corner.
- `left_mid = 7` — Centered along the parent's left edge.
- `right_mid = 8` — Centered along the parent's right edge.
- `center = 9` — Parent's center.
- `out_top_left = 10` — Outside, above the top-left corner.
- `out_top_mid = 11` — Outside, above the top edge, centered.
- `out_top_right = 12` — Outside, above the top-right corner.
- `out_bottom_left = 13` — Outside, below the bottom-left corner.
- `out_bottom_mid = 14` — Outside, below the bottom edge, centered.
- `out_bottom_right = 15` — Outside, below the bottom-right corner.
- `out_left_top = 16` — Outside, left of the top-left corner.
- `out_left_mid = 17` — Outside, left of the left edge, centered.
- `out_left_bottom = 18` — Outside, left of the bottom-left corner.
- `out_right_top = 19` — Outside, right of the top-right corner.
- `out_right_mid = 20` — Outside, right of the right edge, centered.
- `out_right_bottom = 21` — Outside, right of the bottom-right corner.

## `EventCode`

<a id="EventCode" />
```gust
enum EventCode: integer
```

A widget interaction, passed to `on_event` to select which events invoke
the handler and returned by `event_code` inside a handler.

**Variants**

- `every = 0` — Every event (register a handler for all interaction types).
- `pressed = 1` — A press began on the widget.
- `pressing = 2` — The widget is being held pressed (sent repeatedly).
- `press_lost = 3` — The press slid off the widget.
- `short_clicked = 4` — Released before the long-press threshold.
- `long_pressed = 8` — Held past the long-press threshold.
- `long_pressed_repeat = 9` — Sent repeatedly while long-pressed.
- `clicked = 10` — Released without scrolling (a completed tap).
- `released = 11` — The press was released.
- `scroll_begin = 12` — Scrolling started.
- `scroll_end = 14` — Scrolling finished.
- `scrolling = 15` — The widget is scrolling.
- `gesture = 16` — A directional gesture was recognized.
- `key = 17` — A key was sent to the focused widget.
- `focused = 19` — The widget gained focus.
- `defocused = 20` — The widget lost focus.
- `value_changed = 35` — The widget's value changed (slider, switch, dropdown).
- `ready = 38` — A process finished (e.g. a text area confirmed).
- `cancel = 39` — A process was cancelled.
- `deleted = 41` — The widget is being deleted.
- `size_changed = 49` — The widget's size changed.

## `Part`

<a id="Part" />
```gust
enum Part: integer
```

A sub-component of a widget that a style setter can target. A slider, for
example, styles its track through `main`, its filled portion through
`indicator`, and its draggable handle through `knob`.

**Variants**

- `main = 0` — The widget's background and main body.
- `scrollbar = 65536` — The scrollbar.
- `indicator = 131072` — The indicator: a slider/bar fill, a checkbox tick.
- `knob = 196608` — The draggable handle of a slider or switch.
- `selected = 262144` — The currently selected item (roller, dropdown list).
- `items = 327680` — The repeated items of a container-like widget.
- `cursor = 393216` — The cursor of a text area or chart.

## `AnimPath`

<a id="AnimPath" />
```gust
enum AnimPath: integer
```

The curve an animation follows from its start value to its end value.
`linear` covers the distance at a constant rate; the rest start or finish
at a different pace, which reads as weight.

**Variants**

- `linear = 0` — Constant rate throughout.
- `ease_in = 1` — Starts slowly, finishes at full speed.
- `ease_out = 2` — Starts at full speed, settles slowly.
- `ease_in_out = 3` — Slow at both ends, quickest in the middle.

- `bounce = 5` — Reaches the end value and rebounds a few times.
- `step = 6` — Holds the start value, then jumps to the end at the last moment.
- `bezier = 7` — The cubic curve `Anim.set_bezier` describes.

Only available on the ESP32.
</Note>

The wiring and geometry of an ST7789 panel on an SPI bus.

```gust
def St7789

    width: integer
    height: integer
    sck: integer
    mosi: integer
    cs: integer
    dc: integer
    reset: integer
    backlight: integer
    bus: integer
    baud_hz: integer
    x_offset: integer
    y_offset: integer
    invert: bool
    mirror_x: bool
    mirror_y: bool
    swap_xy: bool
    bgr: bool
    buffer_lines: integer

end
```

**Fields**

- `width: integer` — Visible width in pixels.
- `height: integer` — Visible height in pixels.
- `sck: integer` — GPIO driving the bus clock line.
- `mosi: integer` — GPIO driving the data line into the panel.
- `cs: integer` — GPIO driving the panel's chip-select line.
- `dc: integer` — GPIO driving the data/command line, which tells the controller whether the bytes arriving are a command or its payload.
- `reset: integer` — GPIO driving the panel's reset line, or -1 when the module ties it high. Given the line, the panel starts from a known state regardless of what left it running.
- `backlight: integer` — GPIO switching the backlight on, or -1 when the module has no such line.
- `bus: integer` — SPI bus index the panel is wired to.
- `baud_hz: integer` — Bus clock in hertz. Modules are typically specified up to 80 MHz, and tolerate less the longer the leads.
- `x_offset: integer` — Column of controller memory the visible area begins at.
- `y_offset: integer` — Row of controller memory the visible area begins at. A panel shorter or narrower than the controller's own 240x320 memory shows a window into it, and the module's datasheet gives where that window starts.
- `invert: bool` — Invert the panel's colors. The IPS modules this controller is usually paired with need it on to show true colors.
- `mirror_x: bool` — Read controller memory right to left.
- `mirror_y: bool` — Read controller memory bottom to top.
- `swap_xy: bool` — Exchange rows and columns, turning the image a quarter turn. `width` and `height` describe the panel as LVGL draws it, after the exchange.
- `bgr: bool` — The panel's subpixels run blue, green, red.
- `buffer_lines: integer` — Rows of pixels in each of the two draw buffers, trading `width * buffer_lines * 2` bytes twice for fewer transfers per refresh.

<a id="lvgl.set_rotation" />
```gust
def set_rotation(degrees: integer) -> bool
```

Turn everything drawn on the display clockwise by 0, 90, 180 or 270
degrees, reporting whether it was turned. A quarter turn swaps what
`screen` measures, so a widget placed against the screen's own size follows
the rotation.

Only an off-screen display can be turned. A display bound to a card scans
out through the DRM backend, which renders straight into the scanout buffer
and never reads the rotation: a quarter turn would leave the engine drawing
a frame of the swapped size into a buffer laid out for the original one,
which runs off the end of it. A panel mounted on its side is turned by
whatever puts the mode on it — the kernel's `video=...,rotate=90` option,
for instance — and this package draws to the mode it is given. An ST7789
panel is turned the same way, at the panel: `St7789`'s `swap_xy` and
`mirror_x` / `mirror_y` set the controller's own readout direction.

**Parameters**

- `degrees: integer` — Clockwise rotation: 0, 90, 180 or 270.
